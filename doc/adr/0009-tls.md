# ADR-0009: Optional TLS for both roles over rustls

- **Status:** Accepted (issue #81, in the scope the owner approved)
- **Date:** 2026-10-19

## Context

IronFix had no TLS. FIX sessions with internet-facing participants and
crypto venues run over TLS, and integrators want the engine to run the
handshake, not only accept a stream they built (ADR-0007 gave them that
seam). The engine also had no way to hand the counterparty's certificate to
the application, so a client certificate could not be bound to the CompID
its Logon claims.

Constraints any answer keeps:

- With TLS off, the dependency graph is unchanged, and a consumer who never
  asks for TLS compiles nothing of it.
- No crypto provider is forced. rustls offers `aws-lc-rs` (a C and CMake
  toolchain), `ring`, or one the consumer brings; the choice is the
  consumer's.
- The crate DAG holds: TLS types do not reach `ironfix-session`,
  `ironfix-store` or `ironfix-transport`.
- No session-layer change. FIX over TLS is plain FIX framing inside the TLS
  stream, and `EncryptMethod` (98) stays 0.
- ADR-0007 froze the public bound on the stream entry points
  (`AsyncRead + AsyncWrite + Unpin + Send + 'static`), so the peer
  certificate chain cannot arrive as a new bound on `S`.
- The handshake is bounded, and every failure is a typed error.
- No credential (`Password` (554), `NewPassword` (925), `RawData` (96)) and
  no key material reaches a log line.

## Options

1. **A separate `ironfix-tls` crate** depending on `ironfix-engine`. It
   could only drive the engine through the public stream seam, so it could
   not run `authorize_peer` inside the handshake order (after `on_create`,
   before the Logon) without new public hooks on the engine for that sole
   purpose. One more crate to publish in lockstep, for no isolation the
   feature flag does not already give.
2. **TLS in `ironfix-transport`.** The transport frames bytes and knows no
   session; the TLS entry points need the handshake order, the
   `Application` and the typed close reason, which live in the engine. It
   would also put rustls under every consumer of `FixCodec`.
3. **An `ironfix-engine` feature** (chosen).

## Decision

### The feature

`ironfix-engine` gains a `tls` feature, off by default:

```toml
[features]
default = []
tls = ["dep:rustls", "dep:tokio-rustls"]
```

`rustls` 0.23 and `tokio-rustls` 0.26 are optional dependencies with
`default-features = false`: rustls keeps `std` and `tls12` (TLS 1.2 is still
common at venues), and loses its provider features and `logging` (which would
pull in the `log` crate; the workspace logs through `tracing` only). With the
feature on, the normal dependency graph has rustls, tokio-rustls, rustls'
pki-types and webpki, and no provider. `make check-tls-deps`, run in the
`tests.yml` workflow, fails if a TLS crate appears in
`cargo tree -p ironfix-engine -e normal` with the feature off, or a provider
(`ring`, `aws-lc-rs`) with it on.

### Crypto provider policy

The engine never builds a rustls configuration. The caller passes an
`Arc<rustls::ClientConfig>` or `Arc<rustls::ServerConfig>`, and with it the
provider, the protocol versions, the cipher suites, the roots, the
certificates and, on the server, the client certificate policy. The caller
selects a provider in one of two ways:

- builds the configuration with `ClientConfig::builder_with_provider(...)` /
  `ServerConfig::builder_with_provider(...)`, passing
  `rustls::crypto::aws_lc_rs::default_provider()`,
  `rustls::crypto::ring::default_provider()` or its own;
- or enables a provider feature on its own `rustls` dependency and installs
  it as the process default (`CryptoProvider::install_default`), then uses
  `ClientConfig::builder()`.

Either way, the caller depends on rustls itself, with the provider feature it
wants; Cargo unifies that with the engine's rustls. The engine re-exports the
version it is built against as `ironfix_engine::tls::rustls`, so a caller can
name the exact types the entry points take. The tests use `ring` (a
dev-dependency only).

### The entry points

With the feature on, three methods:

```rust
impl<A: Application + 'static> Initiator<A> {
    pub async fn connect_tls(&self, addr: impl ToSocketAddrs,
        config: Arc<rustls::ClientConfig>, server_name: ServerName<'static>)
        -> Result<Connection, EngineError>;
}
impl<A: Application + 'static> Acceptor<A> {
    pub async fn serve_tls(&self, stream: TcpStream, config: Arc<rustls::ServerConfig>)
        -> Result<Connection, EngineError>;
}
impl<A: Application + 'static> AcceptorRegistry<A> {
    pub async fn serve_tls(&self, stream: TcpStream, config: Arc<rustls::ServerConfig>)
        -> Result<Connection, EngineError>;
}
```

They set `TCP_NODELAY` on the socket (the engine holds it, as on the TCP
path), run the handshake through tokio-rustls, and hand the TLS stream to the
private path the stream entry points use: it is boxed once
(`SessionStream::erased`), with the per-call costs ADR-0007 states. A
dedicated `SessionStream` variant for TLS would avoid the box; nothing has
measured whether that matters, so it was not added.

Mutual TLS is a server configuration with a client certificate verifier
(`WebPkiClientVerifier`): a client without an acceptable certificate fails
the TLS handshake, before any FIX byte.

### The peer: `PeerInfo` and `authorize_peer`

`PeerInfo` carries the certificates the peer presented in the handshake,
end-entity first, each as DER `Bytes`, exactly as rustls hands them over.
rustls verifies the end-entity certificate against the roots (building a
path from the intermediates it needs), but returns the list as presented: it
can hold unrelated certificates that took no part in the verification. A
review probe completed a handshake with a trusted `venue.test` leaf followed
by an unrelated leaf from a rogue CA, and `authorize_peer` received both.
The contract is therefore: only `PeerInfo::end_entity_certificate` is
verified, and a binding to a CompID must use it; every other entry is
untrusted metadata unless the application validates it separately.
`tls_tests.rs` holds that probe as a regression test. It holds no rustls type, so it exists
with the feature off too, and the `Application` trait is the same whichever
features are on. `Application::authorize_peer(session_id, peer)` defaults to
accepting; an `Err(RejectReason)` refuses the peer.

It runs:

- on the initiator, after `on_create` and the TLS handshake, before the Logon
  is written, so credentials stamped by `to_admin` go only to a server the
  application accepted;
- on an `Acceptor`, after the TLS handshake and `on_create`, before the
  Logon is read;
- on an `AcceptorRegistry`, after the Logon is routed and the routed
  session's `on_create`, before the Logon is checked, so the application can
  bind the client certificate to the session the Logon claims. A
  lookup-admitted session whose peer is refused is never marked
  authenticated, and is evicted like one `from_admin` refuses.

A refused peer gets nothing written to it (no Logon, no Logout) and no store
is touched. Because ADR-0007 froze the stream bound, the chain reaches the
engine through new entry points, not a bound: `Initiator::establish_with_peer`,
`Acceptor::serve_stream_with_peer` and
`AcceptorRegistry::serve_stream_with_peer` take a `PeerInfo` argument. These
are always compiled, so a caller running a TLS stack of its own (native-tls,
or rustls configured in a way the TLS entry points do not expose) gets the
same hook. The engine trusts that `PeerInfo` as given.

### Timeouts

The handshake runs under its own timeout, `with_tls_handshake_timeout` on
`Initiator`, `Acceptor` and `AcceptorRegistry`
(`DEFAULT_TLS_HANDSHAKE_TIMEOUT`, 10 s). On the initiator it starts after the
dial (which the connect timeout bounds); on both sides the logon timeout
starts after it. The setter exists with the feature off (it holds no TLS
type) and nothing reads it then. It is not on `EngineBuilder`.

### Errors and close reasons

`EngineError::Tls(TlsError)`, with `TlsError::{Handshake { kind, detail },
HandshakeTimeout(Duration), PeerRejected { reason }}` and
`TlsError::failure() -> TlsFailure`. `detail` is rustls' text for the
failure (`invalid peer certificate: UnknownIssuer`, an expiry, an alert),
which carries no key material. `CloseReason::Tls { failure: TlsFailure }` is
reported to `Application::on_session_closed` when a TLS step fails after
`on_create`: the initiator's handshake, or a refused peer in any role. An
acceptor's failed handshake runs before `on_create` and reports no callback,
like a connection that never sends a Logon. `CloseReason::was_active` is
false for it.

### What is logged

A handshake failure is logged at `warn` with the role and rustls' text; a
refused peer with the session, the chain's length and the application's
reason. No certificate and no key is logged. Inside TLS the Logon is handled
exactly as on TCP, so the existing redaction of 554, 925 and 96 holds; a test
captures every log line, at every level, of every TLS test and asserts that
none of those values appears.

## Consequences

- With the feature off, nothing changes in the dependency graph; the public
  surface grows by `PeerInfo`, `TlsError`, `TlsFailure`,
  `DEFAULT_TLS_HANDSHAKE_TIMEOUT`, the `tls` module, `EngineError::Tls`,
  `CloseReason::Tls`, `Application::authorize_peer` (defaulted), the three
  `*_with_peer` entry points and the three timeout setters and getters. With
  it on, the three `*_tls` entry points and the `tls::rustls` re-export. All
  additive: a minor release. Because the entry points take rustls types, a
  rustls major release is a breaking change of the engine's `tls` surface.
- No TLS performance figure is claimed. The TLS stream is boxed like any
  caller stream, and nothing has measured the cost of either.
- Tests: `ironfix-engine/tests/tls_tests.rs` (built only with `--features
  tls`, which `make test` runs) covers both roles and a registry over mutual
  TLS (Logon, a message each way, Logout, each side's `authorize_peer` seeing
  the other's certificate), an untrusted and an expired server certificate, a
  wrong client certificate, a plaintext client, the handshake timeout in both
  roles, `authorize_peer` refusing in both roles (the initiator writing
  nothing), the `*_with_peer` entry points, and the logging of credentials.
- Example pair: `fix44_tls_server` / `fix44_tls_client` in
  `ironfix-example`, behind that crate's `tls` feature (which forwards to the
  engine's and adds rcgen and rustls' `ring` provider as optional
  dependencies). The server generates its certificates at start-up and
  writes only the authority's certificate; the examples workflow builds and
  runs the pair.
- Allocations: `ironfix-engine/tests/allocations.rs` measures the full
  profile from #76 (TLS, a `FileStore`, a frame observer and session Rejects
  between accepted messages, in one window) with control windows naming each
  component, in blocks per frame and with no timing claim. The rustls share
  includes the in-process counterparty's endpoint: dhat counts every thread,
  so the engine's own half cannot be isolated by counting blocks.
- Not done: a `SessionStream` TLS variant without the box; TLS knobs on `EngineBuilder`; certificate revocation (the
  caller's verifier can do it); a `Connection` accessor for the peer.
